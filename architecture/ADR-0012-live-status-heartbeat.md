# ADR-0012: Живой статус процесса: heartbeat-строка каждую секунду и вопросы мотивации в feedback

## Context

После маркеров вида `--- step motivation-feedback-gate (completed)` и во время длинных агент-шагов
обёртка `run_pipeline.py` ничего не печатает — стороннему наблюдателю процесс кажется зависшим.
Причины (по коду, ADR-0011): live-строка в `live_lines.py` появляется только после первого
`step_finish`-события роли, обновляется только на `step_finish` и очищается (`fix_all`) на границе
шага; пока меню гейта открыто, блок скрыт и всё буферизуется; на не-TTY печатается одна строка на
`step_finish`.

На cursor строки нет вовсе: актуальный `cursor-agent` не эмитит `step_finish` с токенами (токены
приходят в `usage`-объектах result-событий, которые читает только `run_statistics.collect_cursor_usage`),
стоимость CLI не отдаёт.

Согласовано с пользователем в трёх раундах мотивации (study.md rev. 3, proposal.md): строка нужна
для **всех** шагов и всегда; анимация — спиннер у имени выполняемого шага, **не сдвигающий** текст;
heartbeat не писать в лог; во время открытого меню гейта heartbeat не показывать; поведение cursor
должно стать таким же, как у opencode (токены видны); в feedback.md копировать **только** нумерованные
вопросы из документа, куда LLM их записывает; списка нет → пустой файл; интервал — фиксированная
константа (без ключа в config.yml); подпись строки без роли — `[harness]`.

## Decision

1. **Всегда видимая строка со спиннером (TTY).** В `live_lines.py`:
   - Пока для текущего шага (из `state.json`, обёртка читает его каждый тик) нет ни одного
     агент-события, блок показывает синтезированную строку
     `[hh:mm:ss] [harness] <spin> [<step> N/M]` — без секции токенов. Первое агент-событие шага
     (любой тип) создаёт строку процесса `[<role>]`/`[<role>#<fork>]` (роль — из имени лог-файла, как
     сейчас) и заменяет harness-строку; при параллельных ревью-форках — по строке на форк.
   - Спиннер: одноколоночные кадры (брайлевские `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` или ASCII `|/-\` — на выбор
     реализации; ширина ровно одна колонка), размещается между подписью роли и частью шага; кадр
     сдвигается не чаще 1 раза в `HEARTBEAT_SECONDS` (= 1.0, константа в `_run_pipeline_common.py`);
     блок перерисовывается каждый тик монитора (0.5 с), так что строка «дышит» и между ходами модели.
   - Секция `cache X · reasoning Y · input Z · output W · price $P` — только для процессов с
     накопительными суммами; `price` — только когда backend отдаёт стоимость (opencode; cursor — без
     price).
   - `fix_all()` на границе шага фиксирует в историю и строки процессов, и harness-строку; маркер
     шага печатается как сейчас; на следующем тике рисуется строка нового шага (окно без строки
     ≤ 0.5 с).
   - Гейты без изменений: пока меню открыто — блок скрыт, вывод буферизуется (политика ADR-0011).

2. **Не-TTY.** ANSI-блок не рисуется (как сейчас). При смене шага печатается одна обычная строка
   `[hh:mm:ss] [harness] [<step> N/M]` — единожды при старте шага, если для шага ещё нет агент-строки.
   Строки на события остаются: opencode — на `step_finish`, cursor — на событие с usage (≤ одна строка
   на ход агента). Heartbeat-строк в лог не пишется (требование пользователя).

3. **Токены cursor (parity с opencode).** `live_lines.add_event` накапливает usage из cursor-событий —
   те же формы, что уже разбирает `collect_cursor_usage`, расширенно:
   - `result`-событие с верхнеуровневым `usage` (`inputTokens`/`outputTokens`/`reasoningTokens`,
     кэш как `cache.read`/`cache.write` либо `cacheReadTokens`/`cacheWriteTokens`);
   - или топ-уровневые поля самого события (`inputTokens`/`outputTokens`/`cacheReadTokens`/…);
   - или вложенный usage со snake_case-ключами (`input_tokens`, `cached_input_tokens`,
     `cache_read_input_tokens`, …);
   - fallback для старых версий cursor: `step_finish` с `part.tokens`/`part.cost` — как у opencode.
   Процесс считается активным с первого любого события (у актуального cursor нет `step_start`). Одно
   malformed-событие пропускается целиком (существующий паттерн) — монитор не падает. Актуальный
   cursor (`--output-format json`) эмитит один result-событие на вызов с usage всей итерации: токены
   обновляются в конце хода, между ходами дышит спиннер — как у opencode между `step_finish`.

4. **Seeding feedback.md вопросами.** В `create_feedback_file` при создании нового файла (правило
   «никогда не перезаписывать существующий» сохраняется):
   - документ-источник выбирается по step id гейта: содержит `motivation` → `study.md`; содержит
     `adr` → `adr.md`; иначе seeding нет (пустой файл, как сейчас);
   - извлекаются только нумерованные вопросы: раздел, чей заголовок (строка `^#`) содержит
     `open questions` или `открытые вопросы` (case-insensitive), — берутся строки вида `^\d+\.` до
     следующего заголовка; раздела нет → вопросы не извлекаются;
   - вопросы записываются в `feedback.md` до открытия редактора; нет вопросов → файл остаётся пустым.
   Хелпер извлечения — чистая функция в `_run_pipeline_common.py` (для юнит-тестов). Распознавание
   гейтов не меняется: `is_feedback_gate` по подстроке `"feedback-gate"` в step id; различение
   motivation/adr — тоже по подстрокам step id (паттерн `FEEDBACK_GATE_MARKER`).

5. **Проводка.** backend (`opencode`/`cursor`) пробрасывается из `run_pipeline.py` через `LiveMonitor`
   в `LiveLines` (у обёртки он уже вычислен) — для опускания price на cursor.
   `feedback_editor.open_feedback_editor` получает `state_dir` и step id гейта (у `_handle_gate_menu`
   они уже есть: `state_dir` — параметр, step id — из state-чтения в момент открытия меню).

## Alternatives

- **Библиотека rich (Live/Progress/SpinnerColumn).** Отклонено: лишняя зависимость; существующая
  ANSI-механика блока уже решает redraw и обрезку по ширине, нужен только кадр спиннера раз в секунду.
- **Анимированные точки `., .., ...` (исходное предложение).** Отклонено пользователем в пользу
  спиннера.
- **Счётчик прошедшего времени вместо спиннера.** Не выбран: пользователь выбрал спиннер.
- **Токены через `opencode export` на каждый тик.** Отклонено: тяжело и медленно; логи уже несут всё
  (то же решение, что в ADR-0011).
- **Heartbeat-строки в не-TTY-лог каждую секунду.** Отклонено пользователем: засоряет лог.
- **Копировать весь study.md в feedback.md.** Отклонено пользователем: только вопросы.
- **Seeding через workflow-шаг (show-file в гейт-сообщении).** Отклонено: вопросы нужны в файле,
  открываемом в отдельном окне редактора; гейт-сообщение в этот момент не видно.
- **Heartbeat поверх открытого меню гейта.** Отклонено пользователем: меню само — видимый статус.

## Consequences

- Плюс: тишины нет ни на одном шаге — harness-строка появляется мгновенно, спиннер дышит каждую
  секунду, на границах шагов окно без строки ≤ 0.5 с; наблюдатель всегда видит, что процесс жив.
- Плюс: токены видны на обоих backend'ах; деградация «нет токенов → только спиннер + статус» встроена.
- Плюс: не-TTY логи чистые (одна строка на переход шага); вопросы в feedback.md — перед глазами в
  момент ответа, существующий файл не трогается.
- Минус: на коротких shell-шагах harness-строка может мелькнуть на <1 с (визуальный шум минимален).
- Минус: формы usage cursor меняются между версиями CLI; при нераспознанной форме строка просто
  останется без токенов (спиннер продолжает работать) — риск ограничен.
- Минус: на cursor токены обновляются раз в ход агента (в конце вызова), между ходами — только
  спиннер (как у opencode между `step_finish`).

## Acceptance Criteria

1. TTY: при старте шага в течение одного тика (≤ 0.5 с) появляется harness-строка
   `[hh:mm:ss] [harness] <spin> [<step> N/M]` без токенов; спиннер — ячейка шириной 1 колонка, текст
   после неё не сдвигается; кадр меняется не чаще 1 раза в секунду.
2. Первое агент-событие шага (любой тип) заменяет harness-строку строкой процесса
   `[<role>]`/`[<role>#<fork>]`; при параллельных форках — по строке на форк.
3. Секция токенов показывается только при наличии накопительных сумм; `price` — только на opencode,
   на cursor опускается.
4. `fix_all()` фиксирует в историю и harness-строку; после маркера завершённого шага строка нового
   шага появляется на следующем тике.
5. cursor usage: все формы п. 3 Decision накапливаются (юнит-тесты на каждую форму); malformed-событие
   пропускается без падения; активность процесса помечается по любому событию.
6. Не-TTY: без ANSI; одна обычная строка `[hh:mm:ss] [harness] [<step> N/M]` на смену шага (не чаще);
   heartbeat-строк нет; строки на события (opencode `step_finish`, cursor usage) сохраняются.
7. Во время открытого меню гейта heartbeat не показывается (текущая политика буферизации сохранена).
8. Seeding: для гейта с `motivation` в step id в новый feedback.md попадают только нумерованные
   вопросы из раздела «open questions/открытые вопросы» study.md; для гейта с `adr` — из adr.md; нет
   раздела — пустой файл; существующий feedback.md не перезаписывается; гейт без motivation/adr —
   пустой файл.
9. `python3 -m pytest tests -q`, `ruff check .`, `mypy spec_utils pipeline_scripts` проходят; добавлены
   тесты: спиннер (частота смены кадра, ширина ячейки), harness-строка и её фиксация на границе шага,
   продвижение в роль, формы cursor usage, не-TTY-строки, seeding и хелпер извлечения вопросов.
10. README описывает: живой статус на каждом шаге (спиннер раз в секунду, метка `[harness]`), токены
    на cursor, не-TTY-поведение, вопросы в feedback.md.
