# ADR-0015: Разделение ADR и плана реализации

## Context

В проекте слово «ADR» обозначает две разные сущности, слитые в одном артефакте задачи: запись
об архитектурном решении (контекст, мотивация, варианты, выбор, последствия — для человека) и
план реализации (детали «как» — для executor). Это порождает противоречивые инструкции
планировщику («ADR не должен содержать деталей имплементации» против «specific enough for a
cheap model to implement without re-asking»), из-за чего публикуемые записи решений разбухают
до пошаговых мануалов с именами файлов и командами, а executor вынужден работать по документу,
которому такие детали запрещены. Требования человека: план — только для executor, как канал
инсайтов сильной модели; ADR — живой артефакт всего прогона, публикуемый в итоговом виде;
при отклонении от плана executor не должен перечитывать план целиком (сессии агентов тёплые);
исследовательский proposal-документ потерял смысл после удаления человеческого гейта
согласования. Устоявшиеся практики требуют того же: AWS — «Separate design from decision»,
Microsoft — «Avoid making decision records design guides», MADR — антипаттерн Mega-ADR
лечится переносом детального дизайна в отдельный документ.

## Decision

Разделяем две сущности на два независимых артефакта, которые пишет планировщик:

1. **ADR** — запись об архитектурном решении для человека и executor (what/why): контекст,
   рассмотренные варианты, выбор с обоснованием, ожидаемые последствия, критерии приёмки
   outcome-level. Без деталей имплементации (имена файлов, функций, пошаговые инструкции) —
   кроме случаев, когда сам артефакт является предметом решения. Живой черновик на весь
   прогон; в публичный каталог решений попадает только итоговая версия в конце прогона.
2. **План реализации** — только для executor (how): конкретные изменения, порядок работы,
   критерии верификации. Не публикуется, не показывается человеку на гейтах, не имеет номера
   и статуса.

Порядок: ADR пишется сразу после исследования, план — сразу после ADR; по плану (ADR как
контекст решения) executor задаёт уточняющие вопросы и реализует. Результат исследования
хранится отдельным артефактом — материалом планировщика; proposal-документ упраздняется.
Ревью сверяют код только с критериями приёмки ADR: план — «мягкий» документ, отклонение от
него при соблюдении критериев ADR нарушением не считается.

Если executor не может следовать плану, он оформляет **уточнение к плану** (почему не выходит,
какие инсайты получены, предложение дальнейших действий), планировщик согласовывает его и при
необходимости переписывает ADR; после согласования executor продолжает реализацию, не
перечитывая план целиком. Отдельные записи об отклонениях и секции поправок к ADR не
заводятся.

Существующие опубликованные записи решений остаются неизменными: это append-only история.

Выбор обоснован тем, что он снимает противоречие инструкций (ADR — строго what/why, план —
единственное место «как»), очищает публичный журнал решений, даёт executor детальный
how-документ, не ограниченный правилами ADR, и следует общепринятой практике отделения
решения от дизайна, включая схему самого движка spec-kit (spec → plan → tasks).

## Alternatives

- **Статус-кво** (одно двойное назначение документа). Отклонено: это и есть решаемая проблема.
- **Один файл, две секции** (план-секция внутри ADR, отрезаемая при публикации). Отклонено:
  детали всё равно рискуют утечь в публичный журнал, фильтрация при публикации хрупка, а
  задача требует разделения сущностей.
- **Три артефакта** (полная цепочка spec-kit: ADR + план + поштучные задачи с фазами).
  Отклонено: executor — одна LLM-сессия, а не поштучный таск-раннер; двух артефактов
  достаточно.
- **План как секция исследовательского документа.** Отклонено: исследовательский артефакт
  упраздняется, а план должен оставаться документом «только для executor».
- **«Expected Implementation Touchpoints» внутри ADR** (Gordon Beeming). Отклонено: задача
  прямо запрещает детали имплементации в ADR; потребность в «how» закрывает отдельный план.
- **План пишет сам executor.** Отклонено: планирование на сильной модели — суть пайплайна
  planner → executor.
- **Публикация ADR в начале прогона + секции поправок после отклонений.** Отклонено
  человеком: ADR — артефакт всего прогона, публикуется один раз, итоговой версией.
- **Промежуточная публикация черновика с постфиксом `-draft`.** Отложено: черновик и так живёт
  только в каталоге задачи; вернёмся, если понадобится ранняя резервация номера.
- **Гейт согласования плана с человеком.** Отклонено человеком: план — внутренний документ
  «только для executor».

## Consequences

- Плюс: публичный журнал решений состоит из коротких читаемых записей, не устаревающих при
  рефакторинге.
- Плюс: исчезает противоречие инструкций планировщику; детали «как» живут в единственном
  разрешённом месте — плане.
- Плюс: executor получает детальную спецификацию без ограничений ADR-правил; инсайты сильной
  модели доходят до слабой без потерь.
- Плюс: отклонения от плана согласуются до публикации ADR, поэтому запись решения сразу
  итоговая и не требует поправок.
- Минус: появляется дополнительный артефакт и дополнительный этап планирования — прогон
  дороже по токенам и времени.
- Минус: два документа могут разойтись (риск смягчается тем, что план пишется после ADR, а
  источником истины для ревью служит только ADR).
- Минус: публикация ADR откладывается до конца прогона — прерванный прогон не оставляет
  записи в журнале.
- Минус: исторические записи остаются «смешанными» — осознанная несогласованность истории.

## Acceptance Criteria

1. После стадии планирования у задачи есть два разных артефакта: запись решения (только
   what/why, критерии приёмки outcome-level, без имён файлов/функций и пошаговых инструкций)
   и план реализации (конкретные изменения, порядок, критерии верификации).
2. План потребляется только executor, никогда не публикуется в каталоге принятых решений и не
   показывается человеку на гейтах.
3. Executor реализует по плану, читая запись решения как контекст; вопросы задаёт по обоим
   документам.
4. Ревью сверяют код только с критериями приёмки записи решения; отклонение от плана при
   выполнении этих критериев не фиксируется как нарушение.
5. При невозможности следовать плану executor записывает уточнение; планировщик согласовывает
   его (дополняет план и, если изменилось само решение, переписывает запись решения), после
   чего executor продолжает реализацию, не перечитывая план целиком; отдельных записей об
   отклонениях и секций поправок не появляется.
6. Запись решения публикуется в каталоге принятых решений один раз, в конце прогона, итоговой
   версией, включающей изменения, внесённые после согласований.
7. Исследование не порождает proposal-документ: его результат доступен планировщику отдельным
   артефактом, а человеческий документ мотивации от него не зависит.
8. Ранее опубликованные записи решений не изменены.
9. Прогон пайплайна задачи завершается успешно; существующие тесты и линтер проекта проходят.
